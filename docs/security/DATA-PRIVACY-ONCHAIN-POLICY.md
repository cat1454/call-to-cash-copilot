# Call-to-Cash Risk Copilot — Data Privacy and On-Chain Policy

> **Status:** MVP security/privacy policy v1  
> **Owner:** Tech Lead + Privacy/Security Owner  
> **Applies to:** `apps/web`, `apps/api`, `packages/*`, PostgreSQL, Redis, S3/MinIO, Agora integrations, Solana integrations, logs, exports, and demo data  
> **Related docs:** [Data Model](../architecture/DATA-MODEL.md), [Booking Contract](../product/BOOKING-CONTRACT.md), [API Contract](../contracts/API-CONTRACT.md), [Incident Runbook](../operations/INCIDENT-RUNBOOK.md)

Call-to-Cash handles conversational, booking, payment, and proof data. This policy states what can be collected, where it can live, what can be written on-chain, who can access it, and how it is removed or escalated. It is intentionally conservative: the hackathon product should prove trust without converting private customer interactions into permanent public data.

---

## 1. Core policy

```text
Off-chain systems store operational data needed to run the booking and resolve support issues.
Solana stores only minimum transaction/proof references needed to verify payment and snapshot integrity.
No raw customer conversational content or direct PII is written on-chain.
```

The product must not claim that a blockchain proof resolves a legal dispute by itself. It only shows whether the current agreement snapshot matches the proof attached at the relevant transaction/reference point.

---

## 2. Data classification

| Classification | Examples | Storage/access rule |
|---|---|---|
| Public receipt-safe | booking public id, masked route/time, deposit status, agreement version, proof result | may appear in authorized receipt |
| Internal operational | risk score totals, reason codes, state transitions, latency metrics | API/operator access only |
| Confidential PII | customer name, phone, precise pickup point, linked account identity | encrypted/masked; strict RBAC; never on-chain |
| Restricted media | raw audio, recording, original transcript, support attachments | private object storage; explicit consent; short retention |
| Secret / credential | AWS keys, Agora app certificate, Solana signer/private key, DB password | secret manager/env only; never logs/client/repo |

## 3. Permitted data by storage location

### 3.1 PostgreSQL — off-chain source of truth

Allowed:

```text
Booking details
Customer contact data (encrypted/masked)
Redacted transcript turns
Conversation turn metadata
Risk assessment history and reason codes
Agreement canonical payload and hash
Payment intent status and transaction verification facts
Trust receipt payload
Consent and audit records
```

Controls:

- encrypt sensitive contact fields where feasible;
- default repository queries return masked/redacted view models;
- use parameterized queries/Prisma only;
- restrict production DB access to authorized operators/services;
- back up encrypted data; test restore separately from application access.

### 3.2 Redis — temporary realtime state

Allowed:

```text
Active transcript buffer
Short-lived call context
Job queue payload references
SSE connection/replay cursors
Idempotency locks
```

Prohibited:

```text
Long-term transcript archive
Raw audio
Durable payment truth
Secrets
Unbounded PII cache keys/values
```

Controls:

- set TTL on every call/realtime key;
- password-protect Redis in local/staging/prod;
- use persistence only for queue resilience, not as business source of truth;
- treat Redis loss as an availability issue, not permission to reconstruct payment status from UI state.

### 3.3 S3 / MinIO — media/object storage

Allowed:

```text
Optional call recording
Raw audio only when recording consent exists
Redacted transcript export
Support evidence attachment
```

Controls:

- private bucket, public access blocked;
- server-side encryption enabled;
- short-lived presigned URLs only;
- no AWS key in frontend;
- object key contains opaque ids, not raw name/phone;
- lifecycle policy deletes restricted media on schedule;
- metadata in PostgreSQL records retention and deletion status.

### 3.4 Solana — minimal proof/payment layer

Allowed on-chain or in transaction-visible memo/reference data:

```text
Transaction signature
Network/cluster indicator
Payment reference generated by server
Expected payment amount and recipient validation facts
Agreement proof hash (SHA-256 or derived opaque proof hash)
Agreement version or opaque booking reference only if non-PII
Receipt verification metadata that cannot reveal customer identity
```

Never on-chain:

```text
Full audio / recording URL
Full transcript or transcript snippets
Raw phone number or email
Customer full name or address
Precise pickup point
Full agreement payload
Raw AI reasoning, prompt, hidden system instructions, model logs
AWS/Agora/API credentials
Wallet private key / seed phrase
```

**Important:** Solana transaction data/memo is public and durable. A hash is only safe if the input is not trivially guessable or reversible in the product context. Do not hash a phone number, small booking id, or short PII string by itself. Hash the canonical agreement payload plus server-controlled salt/version where appropriate, and retain verification method/version off-chain.

#### Phase 8 Devnet provider profile

- The provider is an opt-in demonstration adapter named `solana_devnet`; mock remains the default.
- The transfer request contains only the configured public recipient, demo lamports, a random base58 32-byte reference, static demo label/message, and `ctc:v1` memo fragments derived from random reference/proof hash values.
- The memo/reference must never contain raw or hashed-in-isolation phone, email, name, transcript, route, pickup point, or full agreement payload.
- Server verification persists cluster, signature, confirmation status, slot/block time, observed recipient/lamports/reference, and match flags in minimized provider metadata.
- A Devnet transaction is demonstration evidence only. Customer copy must not claim real VND settlement, investment value, token issuance, yield, trading, lending, or mainnet availability.

## 4. Consent policy

Consent is granular, recorded, versioned, and revocable where technically/operationally possible.

| Consent type | Required for | Default |
|---|---|---|
| `ANALYSIS` | transcription/AI extraction used to operate call flow | explicit before analysis where required by policy/jurisdiction |
| `RECORDING` | saving raw audio or recording artifact | opt-in; not required for basic booking if transcript-only path works |
| `TRAINING` | use of eligible redacted data for future model evaluation/training | opt-in, separate from analysis |

### 4.1 Consent rules

- Do not bundle training consent into basic booking consent.
- Store consent type, status, policy version, capture time, actor, and evidence source.
- A user may decline recording and still proceed with a supported non-recording flow.
- Revocation stops future collection/use. Existing data handling follows retention/legal/support policy; do not claim retroactive blockchain deletion.
- `TRAINING = GRANTED` is necessary but not sufficient: the record also needs redaction, label quality, and review approval before training use.

## 5. Data minimization and redaction

### 5.0 Phase 9 live-audio consent

Live Agora metadata, browser RTC join, Conversation AI Engine start, and final transcript ingestion require a current `ANALYSIS = GRANTED` record. Revocation stops future transcription and triggers browser-track/provider-agent shutdown. The browser receives no Agora App Certificate, CAI customer credential, webhook secret, or agent-property configuration. Provider event signatures and tokens are never logged.

Agora Notifications use a distinct server-only `AGORA_NCS_WEBHOOK_SECRET`; trusted live-relay events use `AGORA_PROVIDER_EVENT_SECRET`. Webhook verification uses raw request bytes and `Agora-Signature-V2`. Never log that signature, authorization headers, raw provider payloads, prompts, tokens, or transcript text.

### 5.1 Before AI analysis/logging

Mask or tokenize where not required for the immediate task:

```text
phone number       → [PHONE]
email              → [EMAIL]
bank account       → [BANK_ACCOUNT]
identity document  → [ID_DOCUMENT]
full address       → [ADDRESS]
wallet where not needed → [WALLET]
```

### 5.2 Do not use for risk scoring

The system must not use the following as fraud/risk proxies:

```text
voiceprint identity
accent or dialect
inferred gender
inferred ethnicity/nationality
perceived nervousness/emotion
speech impairment
```

Risk decisions must be based on booking completeness, term contradictions, payment/reference validation, explicit confirmation, policy/inventory facts, and documented reason codes.

### 5.3 Logs and analytics

- no raw transcript/audio content in application logs;
- no full payment URL or Agora token in logs;
- error reports use request id, public id, and reason code;
- analytics receives aggregated/derived metrics whenever possible;
- demo screenshots/screenshares must use seeded or masked data.

## 6. Access control

| Role | May access | Must not access by default |
|---|---|---|
| Customer | own booking, masked receipt, own consent controls | other customers, raw internal score reasoning, provider secrets |
| Operator | assigned booking/call summary, masked contact, support evidence where needed | unrelated recordings, credentials, raw DB dumps |
| Provider admin | operational booking data needed to fulfill service | raw transcript/training data unless explicitly authorized |
| System worker | scoped data needed for job | interactive user account privileges |
| Developer | local seeded data; production only by approved break-glass process | production raw media/PII by default |

Controls:

- backend enforces authorization; frontend hiding is not authorization;
- use least-privilege IAM for S3 prefixes;
- use separate dev/staging/prod credentials and buckets;
- rotate exposed/revoked credentials immediately;
- audit access to restricted media and manual proof review.

## 7. Retention and deletion schedule

The following is an MVP default. Legal, contract, and provider obligations may require adjustment before production launch.

| Data | Default retention | Deletion / action |
|---|---|---|
| raw audio/recording | 7–30 days with recording consent | S3 lifecycle deletion + metadata tombstone |
| redacted transcript | 90–180 days | delete/pseudonymize per policy |
| original encrypted transcript | shortest period required for dispute/QA | restricted delete workflow |
| risk assessment/reason codes | 180–365 days | retain for audit/evaluation, then minimize |
| payment / receipt / proof record | per accounting/dispute policy | retain minimal immutable transaction reference |
| Redis realtime state | minutes to hours | TTL required |
| audit logs | 365 days or per security policy | append-only, minimized |
| training candidate | only while consent valid and approved | remove from future datasets upon revocation where feasible |

### 7.1 Deletion request behavior

```text
1. Verify requester identity/authorization.
2. Stop future optional collection/use.
3. Delete or pseudonymize eligible off-chain data.
4. Delete object-storage artifacts according to policy.
5. Retain only minimum records that must remain for payment/audit obligations.
6. Explain that on-chain transaction/proof references cannot be deleted, but they contain no direct PII.
7. Write audit record for the deletion action.
```

## 8. Payment and proof privacy rules

1. Generate payment reference server-side with opaque random data.
2. Never derive reference directly from phone number, email, public booking number, or name.
3. Hash a canonical, versioned agreement representation. Include a server-controlled domain separator/salt strategy if threat model requires it.
4. Store the full canonical payload off-chain; store only proof-safe hash/reference on-chain.
5. The receipt shows shortened transaction signature and masked contact by default.
6. Proof `MISMATCH` triggers manual review; it does not expose raw agreement differences to all users.
7. Never place an LLM prompt, model reasoning trace, or audio/transcript in memo/reference fields.

## 9. Security controls by environment

| Control | Local | Staging/demo | Production target |
|---|---|---|---|
| PostgreSQL | Docker volume + dev password | managed/private or hardened container | managed private DB + backups |
| Redis | password + local network | private service | private service + ACL/TLS where available |
| Object storage | MinIO private bucket | private S3 bucket | private S3 + lifecycle + access logs |
| Secrets | `.env` never committed | deployment secret store | managed secret store + rotation |
| Solana | devnet/mock signer only | devnet scoped key | production signer/custody design |
| Logs | local redaction | centralized redacted logs | centralized redacted + alerting |

## 10. Incident triggers

Immediately route to the incident process if any of the following occurs:

```text
credential committed or displayed
public S3/MinIO object exposure
raw transcript/audio appears in logs or chain memo
unexpected on-chain PII discovery
payment recipient mismatch
proof mismatch
unauthorized receipt/media access
training data used without required consent
```

See `docs/operations/INCIDENT-RUNBOOK.md` for containment and recovery procedure.

## 11. Release checklist

Before staging/demo deployment, verify:

- [ ] no AWS/Agora/Solana secret in frontend build, git history, screenshots, or docs;
- [ ] S3/MinIO bucket is private and tested with unauthorized request;
- [ ] presigned URL expires and is object-scoped;
- [ ] transcript/log redaction is exercised with phone and bank-account test strings;
- [ ] recording and training consent are separate in UI/data model;
- [ ] on-chain payload test contains only permitted opaque proof/reference data;
- [ ] receipt is masked and access-controlled;
- [ ] retention job is scheduled/tested for at least one object type;
- [ ] incident owner and contact route are known to the team.
